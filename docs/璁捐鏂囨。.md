# 问数 InsightCopilot · 设计文档

## 1. 问题定义

对话式 BI（ChatBI）让企业用户用自然语言查数据，概念早已不新鲜，但落地率始终低迷。
核心障碍不是“生成不了 SQL”，而是**信任**：

1. **口径靠猜**：用户说“销量”，模型不知道指件数、订单数还是销售额；“复购率”的分子分母每家公司定义不同
2. **SQL 会错**：幻觉表/列、方言错误、答非所问（能执行但算的不是用户问的）
3. **解读会编**：即使数据正确，模型撰写的结论文本也会虚构数字、虚构对比
4. **不会说不**：答不了的也硬答，错误答案包装得很漂亮

本项目的目标不是再造一个 ChatBI，而是回答一个更聚焦的问题：

> **如何让对话式 BI 的每次回答都成为“可验证的结果”而非“看起来对的文本”？**

## 2. 设计原则

1. **不信任任何单点**：每一层机制都假设上游会出错，并独立设防
2. **失败要显式**：反问、拒答、标注都是合法输出；只有“假装成功”不合法
3. **机制可测量**：每层都能被单独绕过（消融）并量化贡献，反对“宣称式可信度”
4. **安全是底线不是选项**：静态校验 + 只读沙箱在任何配置（包括消融实验）下都不关闭

## 3. 系统架构

四层闭环（见 README 架构图），关键组件：

### 3.1 语义层（问得对 · 上）

`data/semantic/semantic_layer.yaml` 显式声明：

- **表/列业务含义**：如 `customer_id` 是单次下单 ID、认人要用 `customer_unique_id`
- **指标口径**：12 个经营指标的中英术语 → 唯一 SQL 定义
- **连接图**：8 张表的外键关系
- **全局约定**：有效订单口径（排除 canceled/unavailable）、时间锚点、金额精度
- **歧义规则**：触发词 → 澄清话术与候选口径

设计取舍：8 张表规模下全量注入上下文是最优解；语义层的真正价值在于
**中文业务术语到英文 schema 的映射**与**口径唯一化**，而非检索压缩。

### 3.2 澄清/拒答门（问得对 · 下）

前置 LLM 分流器：`answer / clarify / refuse` 三态。
规则优先（命中歧义规则才反问）， judgment 兜底；分流器自身失败时降级为 answer，
把风险留给后续校验层——**任何单点失败都有下一层接住**。

### 3.3 生成与自我修正（算得对）

- 生成：系统提示 + 语义层上下文 + 3 个少样本 + 对话历史（指代消解）+ 错误回灌（修正模式）
- 静态校验（sqlglot AST 级）：语法、单语句、只读白名单、表/列存在性（含别名白名单）、危险函数黑名单
- 沙箱执行：独立只读连接、线程隔离 + `interrupt()` 超时、行数截断、DuckDB 原始错误保留（对修正极有价值）
- 修正环：校验/执行失败 → 错误类型 + 错误信息 + 出错 SQL 回灌，最多 3 轮

### 3.4 意图回译（不硬撑 · 一）

最终 SQL 反译为业务语言，再与原问题做一致性判定。
抓的是“SQL 能跑但答非所问”——执行正确的错误回答比报错更危险。
回译文本同时展示在证据面板，让非技术用户也能看懂 SQL 在算什么。

### 3.5 数字溯源（说得对）

洞察文本生成后，程序化抽取全部数字（千分位/百分数/万·亿/约数写法），
与结果集候选值逐一比对（1% 相对 / 0.005 绝对容差，比例双尺度，含同行派生差值与和值）：

- 全部命中 → 原文输出，忠实度 = 1
- 未命中 → 按位置区间替换为 `[未溯源:x]` 标记，绝不让可疑数字静默流出

### 3.6 证据面板

每次回答携带完整轨迹：分流决定、SQL、回译与一致性、执行与修正轮数、
溯源报告、耗时、模型。可信的终极形态是**可检查**——用户不必信我们，可以自己看。

## 4. 评测设计

### 4.1 基准

100 题（中英双语）：A 简单聚合 25 / B 多表关联 25 / C 时间对比 20 / D 歧义澄清 15 / E 超纲拒答 15。
70 道可答题附人工标注 gold SQL，写入前全部在真实库执行验证；gold 结果快照用于自动比对。

### 4.2 指标

- **执行准确率 EX**：生成 SQL 的结果集与 gold 结果集多重集合相等（数值两位小数归一、行序不敏感）
- **澄清率 / 拒答率**：D/E 类期望行为命中率；**误拒率**：可答题被错误反问/拒答的比例
- **洞察忠实度**：可溯源数字占比（full 配置、含洞察子集）
- **平均修正轮数**：自我修正机制的负担与成效

### 4.3 消融

| 配置 | 关闭什么 | 观察什么 |
|---|---|---|
| baseline | 全部机制（裸 DDL → SQL） | 机制的合计贡献 |
| no_semantic | 语义层上下文 | 口径约束对 EX 的影响 |
| no_repair | 自我修正 | 修正环对 EX 的影响 |
| no_clarify | 澄清/拒答门 | D/E 题行为退化 |
| no_grounding / no_backtranslate | 质量层 | 忠实度/一致性（不改变 EX，属于不同失效模式） |

## 5. 工程取舍记录

- **传输双通道**：`requests` 优先、受限网络自动回退 `curl --http1.1`（某些沙箱拦截 Python TLS 指纹）
- **DuckDB 构建绕行**：网络挂载盘（FUSE/OSS）与 DuckDB 写入不兼容，`build_db.py` 先在系统临时目录构建再拷贝
- **推理型模型适配**：`reasoning_content` 字段忽略、空正文识别、max_tokens 留足推理余量
- **前端预构建入仓**：`frontend/dist` 随仓库携带，一键部署不需要 Node

## 6. 局限与后续方向

- 语义层目前靠人工维护；表规模上到数百张时需要 schema linking 检索层
- 数字溯源只做“数对得上”，不做“算得有意义”（如分母选择是否合理）
- 评测集 100 题规模有限，不声称工业级准确率；多轮追问的指代消解评测尚未覆盖
- 后续：口径版本管理与冲突检测、查询缓存、权限行列级控制

## 7. 已知限制与口径说明

本节记录代码审查（2025 轮次）确认后**明确保留**的口径选择及原因，避免后续误判为缺陷。

### 7.1 评测指标口径（eval/run_eval.py）

- **EX 布尔列归一不对称**：`_norm_cell` 对实际值 `True` 归一为 `"1.00"`，而 gold 侧落盘的是 `str(True)="True"`。当前 70 题无布尔输出列，不触发；若未来新增布尔结果题，需先把 gold 生成端改为与 `_norm_cell` 相同的归一规则。
- **gold 结果只存 50 行**（`build_benchmark.py`），实际执行截断 500 行：结果集超过 50 行的题目 EX 必为 False。当前全部 gold 结果 ≤50 行（构建期已验证）；新增题目时若结果更宽，需同步提高两侧上限。
- **EX 列序敏感**：结果集按"行的多重集合"比较，但行内按列位置比对。与 gold 语义相同但列顺序不同的 SQL 判 False。这是有意偏严的口径（与多数 Text-to-SQL 基准一致），报告 EX 时应注明为下界。
- **两位小数归一的双向性**：不同值舍入后可能碰撞判对、未 ROUND 的尾差可能判错，双向误差视为可接受噪声。

### 7.2 数字溯源口径（app/grounding.py，本轮冻结不改）

- **候选值集合偏宽**：日期单元格拆出的年/月/日、同行数值两两差/和、结果行数都计入可引用候选。小整数（1–31）几乎总能"溯源"，忠实度是上界。保留原因：洞察文本大量引用日期部件与行内派生值（"4 月最高""领先 2.16 天"），收窄会误伤真实正确表述；demo trace 与已跑评测的口径一致性优先。
- **Decimal 单元格不识别**：DuckDB DECIMAL 列返回 `decimal.Decimal`，不计入候选，正确数字会被误标 `[未溯源:]`。当前 schema 仅 BIGINT/DOUBLE/VARCHAR/TIMESTAMP，无 DECIMAL 列，不触发；引入 DECIMAL 列时需放宽 `isinstance` 判断。
- **负数不支持**：正则不带符号，`-5` 按 `5` 核验，方向性错误不可检出。

### 7.3 回译机制的行为边界（app/backtranslate.py）

- docstring 中"不一致则触发修正"是设计意图描述；当前实现**只做告警标注，不回炉重生成**（pipeline 仅追加 warning）。原因：回译判定本身有误判率，自动重试会放大延迟且可能震荡；不一致以"结果仅供参考"显式告知用户，符合"拿不准就明说"的原则。

### 7.4 API 暴露面（api/main.py）

- **CORS `*` 且无鉴权/限流**：本项目定位是可公开访问的课程 demo（回放模式无需 key 即可浏览样例），实时模式的 LLM 消耗由部署者自担。若转为多租户生产服务，需加 API key 鉴权、按 IP 限流与 CORS 白名单。

### 7.5 评测运行口径

- **模型**：全部配置统一使用 `deepseek-v4-pro`，并以 `"thinking": {"type": "disabled"}` 关闭思考链（`LLM_THINKING` 环境变量可改）。原因：该推理模型开启思考链后单次调用实测 >200s 且思考 token 计入 max_tokens，评测不可行；关闭后约 12-30s。所有消融配置同模型同参数，横向对比有效。
- **评测代码冻结**：评测跑分在安全审查修复完成前的代码快照上执行（修复含危险函数前缀规则、表值函数拦截、限定列归属校验、SPA 路由穿越修复等）。这些修复只改变"错误 SQL 在哪一层被拦截"，不改变良性问题的管线行为与最终答案，故 EX/澄清率/拒答率口径不受影响；`avg_repairs` 可能存在层间计数漂移，视为下界口径。
- **异常计为失败**：LLM 限流/连接重置在重试耗尽后记 `status=exception`，按未答对计入 EX 分母，不剔除——高峰期实测数字因此偏保守。
